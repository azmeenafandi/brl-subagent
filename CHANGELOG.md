# Changelog

Release history for brl-subagent. Newest first. The full narrative for each release lives in the GitHub release notes.

## Unreleased

- **Internal — the test budget is a per-PR flow rule (U0a/U0b, ADR 0028; cycle 2026-11-14):** the stock ratio is reported against its 1.95 warning band and **never fails**; what the merge gate enforces is each pull request's **flow** (`allowance = 120 + 2 × net source growth`, per surface, `--no-renames`, measured by the cockpit copy rather than the PR tree), with a bare `Test budget:` declaration for a deliberate backfill. The old direct-import floor became a **reachability** floor — every non-test module must be reachable from a test, directly or transitively (7 modules are reached only transitively) — and a pointed audit of the largest test file recovered **9 lines** of genuinely duplicated assertions while withdrawing its own candidate numbers: a "61 no-assert blocks" count was a brace-matcher artifact (**7 of 2,745** are real), five "identical" guardrail bodies assert five different sentences, and the doc-guard quartet has zero genuine duplicates. The generator-facing half of the policy lives in ADR 0028, which supersedes ADR 0027 D7's ratio clause. No user-visible change.

- **A run's progress bank now lives under a private, validated cache root instead of the system temp directory (issue #511):** the extension told agents to bank progress at `/tmp/brl-<label>-bank.md`, and `/tmp` is the wrong place for the one file a run must be able to come back to — world-writable (anyone can pre-create the path, and rename authority comes from write permission on its parent), ambiguous about who wrote it, and on most Linux hosts a `tmpfs`, so the bank does not survive the reboot it exists to survive. The bank now lives at `<root>/runs/<runId>/bank.md`, where `<root>` is `~/.cache/brl-subagent` on Linux and other POSIX, `~/Library/Caches/brl-subagent` on macOS and `%LOCALAPPDATA%\brl-subagent` on Windows, created and validated owner-only (`0700`, every ancestor a real directory owned by root or by you — a foreign owner is a named refusal, `ancestor-not-owned` — while a group/other write bit on an ancestor is a **warning**, not a refusal: a shared or corporate machine's home is often `0775`, and the bank is a convenience, so the warning names the path, the on-disk mode and what a co-worker with write there could do, and the run proceeds): `XDG_CACHE_HOME` is deliberately ignored, because a path the environment chooses is not a path that is yours, and there is **no system-temp fallback** — a root that cannot be placed is a named refusal rather than a quiet move back to `/tmp`. On Linux a root that turns out to be on a `tmpfs` is a **warning** (a home on `tmpfs` is a legitimate setup) that says the bank will not survive a reboot, not a refusal. **Foreground** child processes now receive their run's directory as `BRL_SCRATCH` in their environment, so a child never has to guess or construct the path; it is set as an override rather than an allowlisted variable, so a grandchild resolves its own run instead of inheriting its parent's. The transport auto-retry's resume preamble names the run's **own** bank — the recorded path when the run has one, otherwise the deterministic recomputation from the run id — and stays silent when that directory does not exist (a legacy or pruned run gets no dead path, and the label no longer reaches the filename at all). The pre-flight's third check now proves the **scratch root** is writable — inside the root when it exists, otherwise in its nearest existing ancestor, where the root would be created — instead of writing a file into the system temp directory; a failure names the resolved root, and the old "set TMPDIR or TEMP" advice is gone, because the root is not configurable from the environment. That check is an early warning only: every spawn still resolves the root, re-validates it and creates the run directory, so the pre-flight is never the only place a bad root is caught. **No shipped code path probes, names or falls back to a system temp directory any more**, and a test scans the shipped modules to keep it that way. Settled run directories are pruned after 14 days; a bank an older version left in `/tmp` is neither read, migrated nor deleted — it is simply no longer the convention. No new configuration.
- **Internal — scratch hygiene (issues #509, #512, #513, #516, #518, #520, #522; cycle 2026-11-13):** the tooling no longer writes durable artifacts to the system temp directory. `scripts/lib/scratch-root.mjs` validates a private root (`~/.cache/brl-subagent`) in two zones — above it a real directory owned by root or us with no group/other write, at and below it ours at `0700` — and on Linux refuses a `tmpfs` before creating anything; it then offers explicit-flag create (`O_CREAT|O_EXCL|O_NOFOLLOW`), no-follow append, and an atomic replace through a same-directory temporary file plus `rename`. Records are keyed to the pull request, written under the root by default, and serialized: every write path takes a lock carrying pid, boot id and process start time, re-reads the prior head inside it, and a lock is reported stale only with evidence — a live holder is never removed. Test reports are validated rather than trusted: the count is derived from per-file results (so a fabricated `numPassedTests` is not proof), a hollow or inconsistent report is refused through both the explicit and the scanned path, competing candidates error instead of resolving to "newest", and a provenance sidecar binds a report to the tested commit — reports default to `<root>/reports/<head>.json`, so `/tmp` left the default path entirely. `scripts/audit-scratch-instructions.mjs` scans the tracked skill corpus (exit 1 on a hit) and names the seven ignored local overrides without modifying them. `scripts/review-record.mjs` gains `--break-lock`, and `scripts/suite-report.mjs` captures a report with its sidecar in one command. No user-visible change; the published artifact is unchanged.

- **Internal — the generated-artifact toolchain (issues #487 / #488 / #489 / #500 / #503 / #504 / #505, cycle 2026-11-08):** the numbers that PRs, reviews, handoffs and cycle metrics publish are now generated, and checked by a command rather than by memory, closing the three Rule 11 P0s from the composition-root cycle **and the three defects this cycle surfaced itself**. `scripts/review-record.mjs` emits the review record and `--verify` prints a one-line proof (`verdict · head · findings · sha256`) the conductor recomputes; `merge-guard --check-record` validates it offline, and the gate echoes the record's resolved path and `sha256`. `scripts/pr-evidence.mjs` writes a five-key evidence block into a PR body and **recomputes** every key from the tree — a count with no block fails `missing-block`, a count outside the block fails `unattributed-count`, and the body is never executed. `scripts/handoff-verify.mjs` diffs §STATE's mechanical claims (the `Verified:` range, `dev` resolved past its own handoff commits, the install path, the open set, suite counts, module/ADR counts, per-file sizes). `sprint-metrics` counts codemode-routed dispatches and reconciles them against the extension log's spawns, exiting 3 and appending no row when the delta is unexplained. `merge-guard` gains check (g) — the PR body — proven no looser than the previous gate across nine decision functions. `.pi/skills/worktree/run.sh` returns the **command's** status through a filter (`PIPESTATUS[0]`, non-zero filters reported loudly) and is exercised by CI. The test budget is two surfaces — `src` 1.99/2.0 and `scripts` 0.64/1.0 — with a floor that every gate script is imported by a test. No user-visible change.

- **A settled failure now reports the worktree it may have left behind (issue #474):** every settled-failure surface — a single crash, the `isSubagentError` exit, **each per-unit `SubTaskResult`** at the unit's own cwd, rethrown crashes, `allSettled` rejections and the background wake — carries a read-only, index-safe probe of the run's working tree (`git status --porcelain=v1 -z -uall` with `GIT_OPTIONAL_LOCKS=0`), classified `not-repo` / `unavailable`, formatted by `worktree-report.ts`, and never throwing into the failure path. **Disclosed behaviour change:** a crashed graph node no longer disappears from a dispatch — the dispatch settles `failed` instead of `done`; the old tests pinned the defect. Advisories, not defects: the probe's worst case is ~15 s on the failure path (five 3 s reads; a single porcelain-v2 read is the follow-up), and a stderr path echo is capped at 160 characters.

- **Internal — the composition root (ADR 0027, issues #430 / #482 / #483):** `src/index.ts` fell from 4,720 to 356 lines. The runtime context and the three mode runners, the background pipeline, boot recovery and the terminal notifier, the command and tool registrations, and `delegate_task`'s execute are now factories over one `RuntimeContext`, with per-factory latches and instance identity held by injection; the `delegate_task` handler's complexity fell from 125 to 7, and an ordered-effect-log harness committed before the refactor pins behaviour across twelve dispatch paths. The import convention is guarded in CI (#476). No user-visible change.

## [2.8.0] - 2026-11-08

- **A crashed branch run leaves a durable head state, so the boot can restore the base branch and keep the work (issue #466):** a `gitMode: "branch"` run created `brl-subagent-<8hex>` and kept the starting HEAD only in a local variable, so a run that never settled (a deaf prompt, a crash) left the working tree on the orphan branch with nothing durable naming the base — and the next dispatch read the orphan as *its* base, putting the earlier run's work outside its diff window (re-measured two-process, `W466P-P2B`). The boot could not see it either: the deadline writes the run record terminal, and a terminal record retires the registry claim, so the recovery scan had no candidate. A branch run now writes **one `HeadStateRecord` per repository** — `{version, repoRoot, runId, kind, base, workBranch, owner, createdAt}` — at `.pi/head-state/<sha256(repoRoot)[0:16]>.json`, `0o700`/`0o600`, atomic temp+rename, **inside the per-repo lock, after the dirty check and before the branch exists** (which is why the branch name is now minted by the caller, `newWorkBranchName()`); the foreground branch path writes and clears the same record with `kind: "foreground"`, so "no record" means "no orphan" for every branch run, not only background ones. At boot, between the recovery scan and the recovery notice, the records are reconciled in a **fixed** row order: parse → `repoRoot` resolves → owner **provably dead** → HEAD is exactly the recorded work branch → a deleted-but-checked-out branch (unborn HEAD) still restores, and that row comes *before* the dirty check because `status` reads dirty there for the wrong reason → tree clean → `restoreHead(base)`, verify, clear. Only that last row moves git, only to the **recorded** base (the policy replays a branch, it never chooses one), never with `checkout -f` or `reset --hard`, and the work branch is **never deleted**: after a crash the diff was never captured, so the branch is the only copy of the work. Everything else — a dirty tree, an unreadable record, a vanished repository, a failed restore — leaves the tree alone, keeps the record, and is named in **one** notice on the same `nextTurn` channel as the recovery notice and under the same `config.recovery` gate; the *repair* is never gated, because a tree left on a dead run's branch is a correctness problem rather than a recovery offer. A branch dispatch in a repository whose record is still unresolved and whose owner is not alive now **refuses before the dirty check**, naming the work branch, the base and the exact commands, and ends as the same terminal `failed` dispatch every other refused spawn ends as; a record whose owner is *alive* never refuses, and an unparseable record is never acted on. A record whose repository no longer resolves is swept after 30 days (precedent: `cleanupTempDirs`), and only then — an old record for a *live* repository is never swept by age, because it may be the only name of an orphaned base. **Stated limits:** a `bash` child spawned detached survives a conductor `SIGKILL` and can keep writing while the boot restores (measured 38 B/s), so stray files can land in the restored tree — visible in `git status`, recoverable with `git checkout -- .`, never a commit, and not detectable from the record because background runs carry no `childMarker`; on a host without `/proc` no owner is provably dead, so the policy degrades to name-and-refuse (no pid-only fallback — pid reuse would make it unsound); the store is cwd-relative like the other two, so only a restart **in the same project** repairs; two concurrent pi processes in one repository are not serialized (pre-existing), so the record is last-writer-wins and the earlier orphan becomes an unrecorded `brl-subagent-*` branch; and older orphans are leaked refs — reported by count, never deleted. ADR 0026 records the decision; it qualifies ADR 0023 decision 2 (the deadline still owns no git resource and releases no lock — a *new* owner, the boot, restores only for a record whose owner it has proved dead).
- **A repository locked by a branch-mode run that never settled now refuses the next branch-mode dispatch by name, and one locked repository no longer stalls every spawn (issue #465):** two measured defects in `spawnBackgroundSession`, one amplifier and one wedge. **(d) The convoy.** The module-level `spawnQueue` exists to serialize pi API access (the dynamic import and `createAgentSession`), but the per-repo branch-lock wait sat inside the same `try` — so it ran *inside* that critical section, and because a branch-mode run holds its repository for its whole lifetime, a perfectly healthy run blocked every spawn in the process: measured, a non-git dispatch stayed **`PENDING`** until the branch run settled (#460 M2, and #460 §1.3 shows the everyday 20-minute version). The queue is now released immediately before that wait, behind an idempotent guard the spawn's `finally` shares, so the release happens on every exit path exactly once; the git chain is unchanged — a same-repo branch-mode spawn still cannot touch the working tree until it holds the lock — and the pi-API region stays serialized. **(b) The wedge.** A branch-mode run's lock is released **only** by its settle, so a run the deadline wrote terminal (`stopped` + `completedAt`) that then ignored the abort held its repository forever, and the only signal was a tool call that never returned. The lock's **owner** is now recorded beside it (`gitBranchLockOwners`, keyed like the lock, set only when the lock is actually acquired and deleted only by the matching release so a stale release cannot disown a new holder), the run's **work branch** is stamped on the durable agent record (`workBranch` — `result.gitBranch` is settle-only, which is exactly what a stuck run never reaches), and a branch-mode dispatch whose owner is terminal-but-unsettled past a **30 s grace** is refused **before** its chain link is installed and before it waits, so later dispatches fail fast instead of hanging. Both predicate clauses are deliberate: `completedAt` says a terminal status was written, `_sessionRef` says the settle — the only releaser — has not begun its teardown; the grace bounds the settle-in-flight window (measured 88 ms from the deadline to a cooperative settle, W460P-P6) and was not guessed. The refusal flips the refused dispatch's record `failed`, finalizes its run entry `failed`, completes its transcript `failed` and retires its registry entry **before** throwing, because a throw without the record flip leaves a `running` zombie row for a dispatch that provably never started (#460 §4.4 measured exactly that), and it names the owner run id and its work branch so the human can recover by hand; the caller sees it through the existing spawn-failure result, with no new channel. **Stated limits:** a branch-mode run's lock is held until it settles, so a run whose prompt ignores the abort keeps its repository; from then on branch-mode dispatches in that repository **fail fast with a named reason** rather than blocking; the repository remains checked out on that run's work branch and the lock is cleared only by a **process restart**, and the boot-time repair of the orphan branch is **#466**, not this change. Nothing releases a lock from a timer and no second timer is added (ADR 0023 Decision 2 stands); `stopAgent`, the foreground path, the slot queue (`concurrency.ts`) and the pi-API serialization are untouched, and a non-git dispatch is never refused.
- **The background deadline has ONE owner — the spawn — and only a settle ends a run (issue #453):** the 30-minute default was armed by the caller while an explicit timeout was armed by `spawnBackgroundSession`, with a `deadlineOwner` flag arbitrating between them. That split left one hole nobody could close and one ownership predicate nobody could shorten: a throw anywhere in the caller's tail *after* the spawn returned left the run **unbounded** (measured: zero timers, zero aborts, still `running` after two hours of fake time — the reason #448 deferred it), while the flag existed only to stop the same run being armed twice. `spawnBackgroundSession` now arms the deadline on **every** path — the explicit timeout or the default — before `prompt()`, and the caller's timer, its three `clearTimeout` sites and the flag are deleted; `effectiveBackgroundBudget` collapses both cases into one expression. The caller keeps the 2 s poller, and that poller is the **cleanup owner** for a deadline stop, exactly as it already was for an explicit timeout: the timer sets `status: stopped` + `completedAt`, so the poller's next tick captures the output, claims the finalize, releases the footer counter and repaints. The timer is now **cooperative and prune-free**: it flips the status, notes the transcript, attempts **one** abort, and writes a terminal-run **snapshot** — `status: "failed"` with `errorCategory: "timeout"` (the run vocabulary is `running | done | failed`; there is no `stopped`), passing `isSubagentRunShape` — but it **never prunes the session directory and never releases the branch lock**, because a prompt that ignores the abort may still be writing that directory (a prune there produced a real `ENOENT` for the live child). The single `runFinalized` guard is now **two**: `entryWritten` (set only *after* the append resolves, so a throwing write still lets the settle classify the run) and `pruned` (evaluated by the settle alone, even when the entry already exists — one flag for both would have made a successful deadline write suppress the prune). A late settle **amends** the snapshot instead of writing a second classification: cost, tokens, turns, output, `finishedAt` and `durationMs` move; `status`, `errorCategory`, `stopReason` and `errorMessage` stay the snapshot's. That amendment is what stops timed-out runs reporting `cost: 0`, and the settle now captures the final output **before** it records, so output produced after the deadline lands in the amendment rather than being lost. Because a run can now have three entries sharing its id, **one logical run per id** is the reading contract: `projectLogicalRuns` (exported beside `resolveTerminalRunEntry`) yields the last entry per id, and every raw-entry consumer applies it *before* any window or cap — SLA metrics and the SLA window, cost accounting, history, the three compliance reports, the dashboard, and the visibility bridge — while `maxHistoryEntries` now caps **runs**, so an amendment can never be windowed away from the snapshot it amends. `resolveTerminalRunEntry` takes the **last** non-running entry (`findLast`), and `findSpawnRunById` still takes the first on purpose (it wants the spawn record's `originalParams`). The budget is now **anchored at record creation**: `armDeadline(budgetMs, delayMs)` keeps the reason naming the full budget while the delay is `max(0, budget − elapsed since startedAt)`, so the armed timer matches the displayed `deadlineAt` instead of drifting past it by the setup cost (measured 42–246 ms; `normalizeTimeout` is the wrong path for a remainder, it would read 0 as "no timeout"). **Stated limits that remain:** the abort is cooperative, so a prompt that ignores it keeps running; such a run keeps its session directory, keeps its branch lock until process exit, and has **no registry entry** (the terminal snapshot retires that claim, since the registry means "an owner may still be running"). #448's "a caller throw leaves the run unbounded" limit is **removed** by this change — the arm no longer depends on any caller statement. Out of scope and unchanged: the branch-lock convoy (#460), #439's containment, and the foreground path.
- **A dispatch that never reached the prompt is no longer offered as an interrupted, retryable run (issue #447):** the durable run/registry entry is written long before `session.prompt()`, so a pre-start throw left residue the next boot could only read one way — as a run that started and died. Measured on `78feb6e` (#439 §1.2): an `appendEntry` throw at dispatch (`ENOENT`, a real removed session dir) rejected the spawn while the registry entry survived with no `interruptedAt`, and a `startTranscript` failure (`ENOTDIR`) additionally left the session run entry `running`; `prompt()` was never called in either, and nothing cleared the residue in-process. The reverse direction was equally wrong: nothing distinguished "prompt never invoked" from "prompt accepted, provider silent" — both were `status: "running"`. The records now carry an **acceptance marker**, `acceptedAt`, additive and persisted on both the run entry and the registry entry: written as **`null` at creation** (JSON keeps `null`, so "tracked, not yet accepted" stays distinguishable from a record written before the field), then set to an ISO timestamp by **one** write immediately before `session.prompt()`. That write goes through the same `persistRunRecord` choke point, so the two records cannot disagree — and it is fail-safe: if it throws, the dispatch **does not start**. Every throw between the durable writes and the prompt (the transcript start, the acceptance write, a synchronous prompt throw) now runs one **pre-start cleanup** — clear an armed deadline, tear the work branch down, finalize the run entry `failed` with `Subagent prompt was never issued: <cause>`, retire the registry entry — and rethrows, so the caller still sees the spawn failure unchanged (its classification is #439's). Pruning is provably safe there and only there: nothing can be writing to a run that never started, and no retry is offered for it. The **boot scan** reads the marker as a tri-state: an ISO value is today's behaviour exactly (dead owner ⇒ interrupted, listed, retryable); `null` means never started — no `interruptedAt`, finalized `failed`, not listed and not retryable, and only once its recorded owner is **provably dead** (a live owner may still be inside its own pre-start window, and settling it would stamp a false terminal record the run's real settle could never outrank) (`BootScanSummary.neverStarted` counts the entries actually settled); the field **absent** is a legacy record and keeps today's behaviour, so a pre-upgrade record never loses its retry offer. The display vocabulary is unchanged (`running | completed | failed | stopped`) and there is no fourth status — "started, outcome unknown" remains #439's business. Two limits are stated rather than papered over: the acceptance write lands before the prompt, so a process death in that instant still leaves an accepted record for a prompt that may not have run (the point of no return is inherent — the window shrinks from the whole pre-start region to that one write); and a never-started background dispatch's **agent record** is still left `running` by the spawn-throw paths (a zombie `get_subagent_result` row), which is a separate defect and out of this issue's scope. A third run-entry append per dispatch is the visible cost of the acceptance record; history, retry and recovery surfaces already collapse by run id, while raw-entry consumers (SLA totals, the dashboard's recent-runs list) count it as they already count the spawn entry.
- **A run that started is never reported as a failed spawn (issue #439):** everything `startBackgroundAgent` did *after* the spawn — live-monitor registration, the footer counter, the repaint, the 2s progress poller, the default deadline and the final log — ran uncontained, so a throw in any of them reached the callers' catch and returned **"Failed to spawn background agent"** with `isError: true` while the agent was live. The transport auto-retry reads `isError` as "did not start", so the same throw also made it surface the **source** failure for a run that had started. The shared tail now captures a plain identity record (`id`, `description`, `task`, `status`, `model`, `label`) immediately after the spawn and contains everything else in one outer containment with three independently contained groups — bookkeeping, poller, deadline — each recording its failure into a `tailFailures` ledger; a fault in one group never skips the others, and the tail returns `{ agent, identity, tailFailures }` instead of a bare agent. Both callers (single background and the `tasks` fan-out) format every field from `identity` and classify a non-empty ledger as a **started** run — `isError: false`, the normal "Background agent started: <id>" text plus a "Monitoring degraded" paragraph naming the failure and saying *do not re-dispatch — the run is live; retrieve with `get_subagent_result`* — never as a spawn failure; a fan-out unit's started-degraded report also survives a later unit's failure or a cancellation, and a rejected spawn keeps the existing failure wording unchanged. The bookkeeping group now counts **before** it registers the live row and repaints (counter → row → repaint), so a live row always implies a counted run and the monitor's stale sweep can only ever release that run's own count rather than a sibling's; all five poller/deadline decrement sites share one claim-gated shape that also refuses to decrement a run that never counted. One advisory per run is emitted after aggregation — a `subagent-monitoring-degraded` message plus a warning toast, each on its own try so a closed channel cannot swallow the other — and it is **not** a terminal notice: it never takes the terminal claim, so the run's genuine completion notice is still delivered when it settles (a run whose advisory is emitted but whose settle has no listener degrades to "advisory only" — a stated limit, not a silent one). A second stated limit: the counter is released only by a monitor the run actually owns, so if bookkeeping, poller **and** deadline all fail for one run, its count stays one high on the footer for the rest of the session — the honest reading of a real, unmonitored run, and the alternative (releasing from a group that never attached) is exactly how a sibling's count was stolen. The retry path is otherwise unchanged: it still reads only `isError`, so a degraded retry counts as spawned and the source notice stays suppressed.
- **A batch unit's own high-thinking deadline is dropped by the dispatch pre-flight (issue #434):** the pre-flight judged the **dispatch-level** pair only, while `tasks`/`chain`/`graph` units carry their own `thinkingLevel` and `timeout` and `mergeSubTaskParams` lets the unit value win — so a unit declaring `thinkingLevel: "high"` + `timeout: 600000` under a dispatch with no top-level pair reproduced the 2026-11-06 incident **for that unit alone**: the predicate exited on `params.timeout === undefined`, and every unit site handed `merged.timeout` to the runner. The pre-flight now has a **unit projection** beside the dispatch predicate (one rule, two levels — the same seam, not a second copy): in an opted-in project, a unit that declares its own pair, inherits a high/xhigh declared level, runs **foreground** and carries a **positive** merged deadline has that deadline dropped before its run record is written, so a retry re-derives an absent deadline instead of restoring the cap. The judgement uses the **declared** level, never the capped one (the default cap is `off`, so judging it would silently disable the rule), and `processChecks` is **threaded** from the dispatch — a per-unit re-read of a relative `cwd` measures a different directory. The **#434/#431 boundary** is the unit's own declaration: a unit declaring neither field inherits the dispatch's pair and keeps the old behaviour, chain and graph included, while `thinkingLevel: ""` still means inheritance and `timeout: 0` still overrides an inherited deadline and arms nothing. Background fan-out units are untouched — there the deadline is the legitimate 30-minute budget. At most **one** additional notice is emitted per dispatch, after the unit holds its slot and immediately before its run (never in a pre-pass, so a unit a cancellation skips is never named), and none at all when a dispatch arm already announced; the wording deliberately claims no completeness. `force: true` still keeps the declared timeouts. ADR 0024 records the decision and closes ADR 0022's deferral.
- **A process that has just been sent SIGKILL is no longer classified as a survivor (issue #455):** `escalateKill` decided its survivor list by sampling death **in the same pass that sent the signal**, but SIGKILL delivery is asynchronous — a 40-iteration probe read `alive` **40/40** times at that instant (state `R`, delivery pending, or `Z`, awaiting reap), so the survivor list was decided by a race. In the suite that was the `recovery.test.ts` `#299 A1` flake (fails 2/2 under full-suite load, passes 3/3 alone) — which is to say the "flaky test" was a **producer** defect; in production it is a false "could not kill" warning for a process that is already dead. The SIGKILL pass is now three phases — **A** force-kill, **B** a bounded post-SIGKILL drain of `verifyDeath()` for exactly the force-killed targets, **C** classify — with `drainMs` (default 100 ms; non-positive restores the legacy single-sample classification) threaded through `RecoveryDeps`. Both the new drain and the pre-existing grace loop are bounded **twice**, by the clock and by `ceil(window / pollMs)` iterations, because the clock bound alone is defeated by a no-op injected sleep: measured 61,657 samples inside one 100 ms window (787,234 on the reviewer's box), so a frozen clock now costs at most the poll count and never a hot spin. The acceptance signal is the original test, **byte-identical** (`git diff dev...HEAD -- src/__tests__/recovery.test.ts` empty), now green under full-suite load where it failed before. **Stated cost:** worst-case added latency is `drainMs` (100 ms) per escalation and only when a SIGKILL was actually issued — zero when nothing needed killing; the refused-group rule and the unconditional final group SIGKILL still run **after** classification, because a refusal is a decision, not a timing window.
- **A preset field declared on the interface can no longer be silently dropped (issue #436):** `presetFromFrontmatter` re-stated the `SubagentPreset` field list by hand, so a field added to the interface but missing from the mapper was dropped without an error — `outputFile` was exactly that, and a preset author writing `outputFile:` got neither an error nor a file, while the merge layer (`params.ts:441`) and the template loader both already expected the value. The mapper is now a **table pinned by the type system**: `PRESET_FIELD_MAPPERS satisfies PresetFieldMappers`, where `PresetFieldMappers` is a mapped type over `Exclude<keyof SubagentPreset, OmittedPresetField>`. Adding a field without a mapper is a compile error (`TS2741`); a mapper for a field the interface no longer declares is an excess-property error (`TS2353`) — both proven by adding a probe field and a stale key in the real tree. `outputFile` is mapped, a non-string value is refused at load, and a preset-derived `outputFile` reaches `validatePreTask` and inherits the same hard write-tool conflict as the call parameter. `timeout` stays the one deliberate omission, allowlisted with its ADR 0022 §6 reason and pinned to exactly `"timeout"` by a type-level assertion, so the omission cannot grow silently; its tests are byte-identical, and a preset declaring `timeout: 600000` still loads without one. The template loader got the same table and the same pin — the sibling the issue asked to check. **Ramification:** a preset that already declares `outputFile` now *works* (previously silent) and will hard-error if it also excludes `write` — the intended H1 conflict, not a regression — and `timeout` remains unreachable from presets by design, because mapping it would re-merge a deadline the ADR 0022 drop arm believes it removed.
- **A terminal-notice dedupe overflow no longer forgets the claim it just made (issue #440):** `markTerminalSeen` cleared its whole dedupe set when it exceeded the 200-entry cap — **including the id claimed in that same call** — so at the 200→201 boundary an immediate duplicate terminal event for the same run id claimed again and was delivered twice. Reproduced through the real claim surface (`claimTerminalNotice`, not the private set): claim 200 ids, claim `id-overflow` → `true`, claim it again → **`false`**; on the old code the second call returned `true`. The set now evicts the **oldest** entry (a `Set` iterates in insertion order) and clamps a degenerate cap to at least 1, so retention stays bounded and the claim just made is never the eviction victim. The documented contract — "an evicted id may be delivered again" — keeps its meaning with a different victim, and the invariant is now stated as "the claim just made survives". **Blast radius:** terminal-notice dedupe only (wake and crash notices for background runs); no delivery decision, no `DEDUPE_CAP` value and no path or format change, and reverting is a one-line edit.

- **A deadline abort no longer depends on the bookkeeping before it, and a direct spawn is bounded (issue #448):** two measured defects in the background deadline path. **(1) A throwing bookkeeping call suppressed the abort.** The timeout handler ran `updateAgentStatus('stopped')` → `completeTranscript('stopped')` → `session.abort()` inside one `try`, so any throw in the first two steps skipped the abort entirely. Reproduced on this tree with the run's transcript path made a real directory (`EISDIR` from `appendFileSync`): the record said `stopped`, `abort()` was **never called**, and the child kept running. `session.abort()` is now attempted **exactly once, outside** the fallible block, and a bookkeeping failure is surfaced in the log (`spawnBackgroundSession: deadline bookkeeping failed for <id>`, the same file log the settle paths use — no new user-facing notice). The status still flips **before** the abort, because the settle path classifies the run as stopped from that pre-set status. **(2) A direct spawn armed no deadline.** The 30-minute default was the caller's (`index.ts`), armed after the spawn returned, so `spawnBackgroundSession` called directly with no `timeout` armed nothing (measured: zero timers, `abort: 0`, `status: running` after an hour). The spawn now arms `effectiveBackgroundBudget(undefined)` itself — the single definition of the default, never re-spelled — **before** `prompt()`, and a new internal `deadlineOwner: "caller" | "spawn"` (default `"spawn"`) tells it when the caller already owns that default: the one production call site (all dispatch, fan-out and retry paths route through it) passes `"caller"` and keeps its own timer, so an ordinary dispatch still has exactly one deadline. The timer remains **abort-only** — status, transcript note, `session.abort()`, with no finalization and no session-dir pruning — is cleared by both settle handlers, and is cleared **in the synchronous-throw catch before that catch's own cleanup**, because no settle handler attaches on that path. An explicit timeout is still honoured verbatim and a raw value `>= 2^31-1` still normalizes to "no timeout" with the default applying. **Two limits, stated in writing:** a caller-side throw *before* the caller arms its timer still leaves the run unbounded (`timers: 0, abort: 0, running`) — deferred to #453 — and the abort is **cooperative**, so a non-settling prompt still stays `running` and is deliberately not finalized, because finalizing there would prune a session a still-writing child may hold (#453). Two small, deliberate presentation changes ride along: the timeout reason now reports the **normalized** budget, so a raw `>= 2^31-1` value reads `Timed out after 1800000ms` rather than the sentinel; and the zero-timeout test in `session-manager.test.ts` now asserts the **owner rule** instead of "no timer", because a direct spawn is supposed to arm one — the assertion was rewritten because the behaviour it pinned was the defect. Escalation, `stopAgent`/`stop_subagent` and the foreground path are untouched.

- **A background run that settles with no assistant output is a failure, not a success (issue #449):** pi 1.5.0 can remove the only assistant message from the **projected** session before a run settles — a provider turn that stops on `max_tokens` while reporting fewer output tokens than the model's catalog `maxTokens` is classified as a recoverable length and omitted (`_omitRecoveryAttempt`), and when the branch is too young for the recovery compaction to find anything to summarise, that omission stands and `prompt()` still resolves. The settle site read the projection, found no assistant message, got an `undefined` stopReason and classified the run as **completed**; measured end to end on the real SDK over a loopback provider, that is `status: completed`, `exitCode: 0`, `usage.turns: 0`, `finalOutput: ""`, a `done`/`stop` run entry with no category, and a completion wake saying `category: success`. The classifier now takes an **assistant-evidence** signal (`"present" | "absent" | "unknown"`, defaulting to `"unknown"` so every other caller is untouched) that only the background settle site supplies, read from the same projection the stopReason comes from; `"absent"` means exactly one thing — an array that was read and holds no assistant message. The displayed outcome for this class changes from **completed** to **failed** (`incomplete`, `exitCode 1`, a failure wake), and the status vocabulary is unchanged: no new status, category or field. An already-known terminal reason always wins (an explicit `stop` still completes; `error`/`length`/`toolUse`/`deferred`/`pending` keep their own categories; a pre-stamped stop stays `stopped`), and a zero-output run **with** an assistant message (empty content, empty text, thinking-only, tool-use-then-empty) still completes. The reason is a fixed headline — `Run settled with no assistant output — the provider's response may have been truncated and omitted by the SDK (see #449)` — which states the observation, offers truncation only as a possibility, and **wins over** a stale `session.state.errorMessage` (that text may be appended, never substituted). It matches no transport signature and its `incomplete` category is excluded by the retry class gate, so the **automatic transport retry never fires** for this class. **Limits:** the guard is structural, not diagnostic — the omitted message is unrecoverable, so it cannot distinguish a truncation omission from any other resolve-with-no-assistant-message and does not prove truncation; a throwing/missing `messages` projection still takes the settle catch-all and is not covered; and the run's session directory is still pruned on this path, so the fix removes the false success, not the data loss (retention is a separate decision). The **foreground** path is deliberately untouched: its child emits `message_end` for that turn, so `runner.ts` already records `stopReason "length"` and `isSubagentError` already fails it — and widening that predicate would reclassify deliberately handled input (an extension returning `{action:"handled"}` exits 0 with zero message events). A minimal reproduction (loopback fake provider + the real SDK) lives in `.development/investigations/repro/issue-449/`.

- **An unknown `thinkingLevel` is rejected instead of silently running at pi's default (issue #443):** the level was resolved by clamping — `resolveThinkingLevel` clamps but cannot fail — so an unknown declaration (`"bogus"`, `"MAX"`, `"High"`, `" high"`) had index -1 and resolved to `undefined`. That value reached the child as `--thinking undefined`; pi warned `Invalid thinking level "undefined"` and ran at **its own** default, so the configured cap was bypassed rather than a launch refused. Measured on pi 1.5.0 with the cap set to `off`: the child initialised at `high`. Background behaved the same (an SDK session at the model default while the run record said `medium` and `originalParams.thinkingLevel` kept the bad value), a bad **second** unit still started the whole batch, and a restored record could re-launch it. A declared level is now checked **before resolution**, at every seam that can reach a launch: the per-call value; the selected preset's (named **or** auto-routed — an in-memory preset object never passed the preset-file validator); each `tasks`/`chain`/`graph` unit before any spawn, and the background fan-out's per-task pre-pass (so a bad second unit rejects the batch with nothing started); a value restored by `retryRunId`; and the transport auto-retry's rebuilt params, where a rejection starts no SDK session and still surfaces the **original** failure notice. Matching is case- and whitespace-exact, `""` keeps its existing meaning (top level → the configured maximum, per unit → the global level) and an omitted field is unchanged, while pi's own `max` is now a rejection naming the supported set. The schema's `thinkingLevel` gained an `enum` as a first line of defence — it names the whole set in pi's error and keeps `""` valid — but it validates raw tool arguments only, which is why the runtime guard exists; the cap semantics, `resolveThinkingLevel`'s clamp, and every valid declaration are untouched. **Limit:** a level already erased into a persisted unit record (stored resolved as `undefined`) cannot be truthfully rejected later — that is a documentation limit, not a migration; a corrupt non-string persisted `maxThinkingLevel` is a follow-up.

- **`tools: []` now means no child tools (issue #442):** an explicitly empty allowlist used to be indistinguishable from an omitted one at the spawn boundary — `resolveSubagentParams` kept `tools: []`, but `buildSubagentArgs` only mapped a *non-empty* list to `--tools` and otherwise added no restriction at all, so a dispatch that asked for zero tools got pi's full defaults. Measured on Pi 1.5.0 against the real foreground `runSubagent` path: with `tools: []` a scratch extension tool and a direct-exposure MCP tool both executed. An empty list now maps to pi's `--no-tools` **before** the `noBuiltinTools` branch, so `[]` disables built-in, extension, custom and MCP tools and can never widen into `--no-builtin-tools` (built-ins off, extension tools *on*); `--exclude-tools` stays additive and cannot re-enable anything. Omitted, non-empty `--tools`, `noBuiltinTools` and `excludeTools` behave exactly as before, and the edit-implies-write rule is unchanged — `[]` plus `outputFile` is still rejected before launch, because no write tool exists. Background needs no change: `spawnBackgroundSession` already passed the empty list through to the SDK session (`tools: []` = zero active tools) and still loads no extensions, no skills and no MCP servers. **This is a tool-access setting, not a security sandbox:** in the foreground, configured extensions and MCP servers still initialise and connect (users rely on their startup and on extension hooks), so `[]` denies the model their tools rather than preventing the code from running, and it is no defence against an extension that reactivates tools deliberately. The README states the distinction and the schema's `tools` description points at it.

- **A shut-down runtime can no longer steal the next session's completion wake (issue #437):** the extension's three terminal event-bus listeners (`subagent:completed` / `failed` / `stopped`) were anonymous closures that nothing ever removed, so a clean session replacement (`/new`, `/resume`, `/fork`, `/reload`, quit) left the old runtime's listeners on the shared bus. The bus preserves registration order, so the stale listener won the shared one-notice-per-id claim for a run the NEW session had started, then delivered it through — or threw on — its dead `pi`/`ctx` handles, and the live runtime's wake was lost. Each factory instance now keeps the exact listener references it registered and unsubscribes only those, synchronously, as the first step of `session_shutdown` (before the reap await or any fallible cleanup), idempotently on a repeated shutdown; other subscribers and the next runtime's fresh listeners are untouched, and the delivery matrix, transport auto-retry, claim timing and crash-notice dedupe are unchanged. Users should still avoid `/new` while background runs are active: delivery or cleanup for a run already in flight remains out of scope, and the retry-start/unknown-outcome problem stays with #439.

- **A foreground dispatch can no longer be killed by its own timeout — and the pre-flight can no longer turn a valid dispatch into a rejection (issues #431, #433):** the durable-shape pre-flight (#412) only fired for an **explicit** `background: false`, so the exact 2026-11-06 shape — `high` thinking, `background` omitted, `timeout: 600000`, an effective `writes` mode that the #361 default keeps foreground — kept its deadline and the run was killed at 10m0s. The pre-flight now has **two outcomes** in an opted-in project: where a background run is possible (explicit `background: false` with `auto`/`writes`) the dispatch is switched to background and the timeout dropped, exactly as before; where it is not — an effective `always`, or an omitted `background` that the `writes`/`always` default keeps foreground — the run **stays foreground and the explicit timeout is dropped**, because a foreground run has no default deadline at all, so no clock kills it while its approval gate stays exactly where the user put it. A drop is announced on both channels with the actual dropped ms value; `force: true` keeps the explicit timeout on either arm, and it never fires on an outcome that changed nothing. The same rule closes a pre-flight bug that could reject a valid call: an explicit-foreground dispatch with `approvalMode: 'always'` was switched into background and then refused by the background gate (no dialog there) — it now stays foreground with no deadline instead, so **the pre-flight never switches a dispatch into a rejection**. `chain`/`graph` stay exempt (per-unit dimensions still bypass the pre-flight — #434), the `auto`/`writes` switch arm is unchanged, and without the project's `processChecks` opt-in nothing changes. ADR 0022 records the decision and supersedes ADR 0018's omitted-background exemption.

- **A running subagent's budget is visible on every surface (issue #423):** the budget existed only as a dispatch-time parameter and was rendered nowhere afterwards, so a run could hit its deadline without the human (or the conductor) ever seeing what the deadline was. A background run now persists its **effective** budget (`timeoutMs`: the explicit timeout, else the 30-minute default) on the record at spawn, and every live entry carries an absolute `deadlineAt` — background runs and foreground/chain/parallel/graph units alike, through the existing `registerLiveRun` registration (a foreground run has **no** default deadline, so a deadline appears there only when a timeout was actually passed). The footer shows the age of the **oldest still-running** agent plus the nearest deadline — `ran: 4m 12s · deadline in 34s` — turning into `ran: 4m 12s · deadline: stopping` at or past zero; the monitor rows and the dashboard's Active Subagents panel show `4m 12s / 30m (86% left)` per row, skip settled-but-lingering ids, and order by the soonest deadline; the drill-in now opens the row that was actually **rendered**, so a spawn or a finalize between paint and Enter cannot open a different agent than the one highlighted. `get_subagent_result` appends `Budget: 30m — 4m 12s used, 25m 48s left` whenever the record states one (an old record gains no invented deadline), and the completion wake carries the same line — `Budget: 30m (exhausted)` only on timeout evidence, never for a user abort or a completed run — as its own paragraph for `stopped`/`failed` runs. Nothing about timing changed: the 30-minute default, both deadline timers, the foreground kill escalation and the no-flag behaviour are exactly as before, and a displayed deadline still precedes the real kill by the in-prompt preflight.

- **A project's engineering bar is injected at the spawn seam, not selected by preset (issue #421):** the SOLID/DRY quality bar and the design-assumptions checklist lived in the repo-local `project-implementer`/`project-reviewer` presets, so four implementation dispatches that ran on the shipped `dev-agent` preset silently lost them; the checklist itself was untracked and got deleted as a "ghost". Both are now one tracked reference, `.pi/skills/worktree/references/engineering-bar.md`, appended to the child's **system prompt** as a conductor-authored `<engineering-bar>` section by both spawn seams — the background `appendSystemPrompt` array (ordered after `<resume-context>`) and the foreground `--append-system-prompt` file at the shared `runSubagent` chokepoint. The section is gated by the project-local `processChecks` flag (ADR 0019, fail-open): in a user's project neither the section nor the file read happens, and no preset choice can drop it in this one. A missing or empty reference logs one warning and skips the section — never a crash, never a silent skip. The section now also carries the review addendum (Gate A, the `SOLID/DRY violations flagged: N` line, and the structural-closure block for refactor PRs), so a reviewer gets it without the reference doc being read. The file is outside `package.json.files`, so it never ships; tests pin both directions, the file's required sections, and the packed tarball.

- **A `noJev` bypass has to state a reason in words (issue #419):** `delegate_task`'s bypass for the Jev dispatch-line pre-flight was declared a non-empty reason string and described as refusing `true` and an empty string at the schema layer (ADR 0018 §2). That held only for the empty string. The harness validates tool arguments with coercion on, and pi-schema's string rule stringifies booleans and numbers before the handler is called, so `noJev: true` arrived as the string `"true"`, satisfied `Type.String({ minLength: 1 })`, and dispatched a run whose warning named "true" as the reason (live probe, 2026-11-02) — while a value with no text form, such as `{}`, reached `config.noJev.trim()` and threw `TypeError: config.noJev.trim is not a function` instead of being rejected. The reason is now read through a runtime guard: a string, trimmed non-empty, and **not** a coerced primitive (`true`/`false`/a bare number). Anything else is a clean **error** — the normal missing-line refusal plus an `invalid noJev: …` diagnostic — so a boolean can neither bypass the check nor crash it, and a genuine reason still downgrades the rejection to a warning that names it. The read stays inside the project's `processChecks` opt-in (ADR 0019), so a user's dispatch is never examined; the schema's description now says the reason is validated in the handler, ADR 0020 records why, and the suite pins the coercion through the real validator rather than the declared JSON shape. ADR 0018 is untouched — superseded on this one claim, not edited.

## [2.3.8] - 2026-09-23

- **Background fan-out — `tasks` finally runs in the background (issues #196, #198):** `delegate_task({ tasks: [...], background: true })` now starts one independent background agent per task. The call returns immediately with **one id per task in task order**, and you are woken **once per agent** as each finishes. Before this, `background: true` combined with a batch mode was *silently ignored* — the call ran foreground and blocked while the caller believed it was background; that combination now rejects loudly, and for `tasks` it became the feature. The whole batch is resolved and validated **before any spawn**: a bad `cwd`, `outputFile`, or pre-task check rejects the call naming the task, with nothing started. Per-task overrides are honored (`model`, `thinkingLevel`, tools, prompts, `outputFile`, `timeout`, `cwd`, `priority`, `label`), and each agent's run entry snapshots its *own* params, so retrying one member restores that member — not the batch. Three checks reject up front: `approvalMode: 'always'`; `gitMode: 'branch'` (the per-repository git lock is awaited inside the first spawn and held until that agent settles, so a fan-out would block the call); and the session cost limit, now checked as per-task estimate × N. A spawn failure or abort mid-loop stops further spawns and reports the failed task plus the ids already started — those agents stay detached and still wake the conductor. `chain` and `graph` cannot be combined with `background: true` (they need sequential and dependency state) and are rejected loudly.
- **Run-entry lookups are explicit (issue #185):** every run appends two entries sharing its id — a spawn entry (`status: "running"`, carrying `originalParams`) and a terminal entry at settle. `findRunById` returned the *first* match, so finished runs were looked up as running: the TUI's stale-foreground fallback lost terminal output, and the #52 staleness sweep never reclaimed a poller-dead live entry. The terminal-preference rule now lives once in `resolveTerminalRunEntry`, with `findSpawnRunById` (retry params) and `findTerminalRunById` (finalized entry) used by intent at each call site.
- **Failed-run records are coherent (issue #187):** `finalTurnError` was derived from the *coerced* failure reason, so a hard-cap timeout or a synchronous spawn throw was recorded `finalTurnError: true` even with no provider error — it now derives from the raw terminal reason. The foreground `finalizeRunRecord` never set `stopReason`, so a failed foreground run was recorded failed with no reason; it now shares the background path's `coherentFailureReason` helper.
- **Two new ratchets (issues #183, #186):** every runtime string literal under `src/**` is now AST-scanned for internal process vocabulary (`Rule <n>`, `retry taxonomy`, `friction log`, `handoff`, `worktree`, `E<nn>`) and issue references — the exact leak class #174 shipped for months, including terms split across string concatenation. The terminal-status ratchet was a line-regex that matched one of eight spellings and ignored `exitCode`-as-success; it is now an AST walk covering comparisons (any quote style or alias), membership tests, failure-list definitions, and numeric exit-code comparisons, with recorded allow-list reasons for genuine exemptions.
- **Development:** `@earendil-works/*` devDependencies to 0.87.0 — the runtime had been ahead of the type-check gate; all five 0.87 breaking changes were verified to miss us, and a live probe on the new runtime confirmed the background settle path. 1102 tests across 50 files.

## [2.3.7] - 2026-09-20

- **A died run is no longer reported as a success (issue #179):** the SDK resolves `session.prompt()` on a mid-run provider death — `handleRunFailure` records an assistant message carrying `stopReason: "error"`, then the run *resolves*. Our settle path had no `error` branch: it derived status from `exitCode` alone and set `completed` unconditionally, so a death landed as `completed` / `exitCode: 0`. Template resolution now runs first, and the retry block sits between it and the sanitize (deliberately **not** before it — `resolveRetryParams` returns a fresh object that drops `template`). An explicit `task` that would have failed validation while a template wins now warns through the same `pi.sendMessage` path as the unknown-parameter warning, rather than vanishing silently.

### H1 — Pre-task validation

Deterministic pre-spawn checks that validate tool configuration and thinking level match the task description. Warns about **thinking level mismatches** (e.g., `off` thinking on a complex debugging task) and **missing tools** for the requested task. **Hard-rejects** combinations that cannot work — e.g. `outputFile` when the `write` tool is unavailable (a preset like `security-auditor` excludes it) — with a visible error before any tokens are spent.

### H2 — Integration test suite

Two-tier test coverage:
- **Tier 1:** jiti import verification — confirms the extension loads without errors.
- **Tier 2:** Subprocess execution — verifies the extension can spawn and communicate with a subagent process.

### H3 — Post-mortem diagnostics

When a subagent fails, analyzes the failure and suggests concrete fixes:
- Git mode mismatch (e.g., `gitMode: 'branch'` when repo is dirty)
- Thinking level too low for the task complexity
- Timeout issues and recommendations for increasing limits

### H4 — Conductor guardrails

Behavior rules embedded in `promptGuidelines` and `SUBAGENT_INSTRUCTIONS` that guide the conductor LLM to configure subagents correctly before spawning. Prevents common misconfigurations at the prompt level.
