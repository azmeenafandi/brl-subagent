## 1. Recommendation

**Design B — owner-scoped terminal delivery with a synchronous, event-first claim and a committed-spawn
invariant.** In one sentence: *the generation that pi activated owns the subscribers; the subscribers
validate the context, agent and run synchronously and take the shared claim in the same turn as the event;
anything after the claim is irreversible and is never reported as a source failure once a spawn or send has
possibly happened.*

Cost: ~90 lines in `src/index.ts`, one test-only counting export in `src/event-bus.ts`, two test files
(31 named assertions in the verified prototype). No new dependency, no persisted format change, no change
to the notification payload, the 9-row `completionNotify` matrix, the one-retry policy, the crash-notice
envelope, or the abandon suppression. No cross-replacement delivery, no durable queue, no automatic `/new`
guard — the maintainer's scope is taken as given.

Why this and not the alternatives: it is the only verified option that (a) preserves the *event-first*
claim winner (the baseline behaviour the critique proved candidate C broke), (b) leaves an ID claimable
when validation fails, (c) removes obsolete listeners by exact identity, and (d) distinguishes a rejected
spawn from one that already started — while keeping a diff small enough to review in one sitting.

### 1.1 What changes for whom (the maintainer's transition policy, applied)

| Run class | Before | After |
|---|---|---|
| begun in the **current live session**, after a replacement | wake lost, auto-retry silently dead (measured: 0 sends, 0 retry spawns) | wake and auto-retry delivered by the live generation; at most one notice per id inside the 200-id window; retry classified as committed vs rejected |
| begun **before** a replacement and settling across it (straddling) | no terminal event at all (the settle write throws at `pi.appendEntry` before the emit) | **unchanged** — still no guaranteed delivery, no handoff, no queue, no new guard. The fix does not make it worse and does not claim it |
| `completionNotify` `off` / `failed` | message delivered as `nextTurn` (no turn) | **unchanged**, and asserted for all 9 status × knob rows at the real send boundary |

## 3. Verified mechanism (what the source actually does)

1. **Factory re-invocation shares the module graph on `/new`.** `eventBus`'s `listeners` map and
   `terminalClaims` live at module scope (`src/event-bus.ts:11-13`, `src/notify-completion.ts:279`);
   pi's loader re-invokes the cached module factory for a new session runtime, so the previous
   generation's listener closures stay in the same `Set`. `/reload` re-evaluates the module (fresh graph,
   fresh set). Re-verified here only indirectly — the control copy (`base2`) reproduces A2/A3 failures that
   require exactly this sharing, and the patch (`s1`) removes them.
2. **The lost wake is a claim-ordering failure, not a send failure.** The obsolete listener wins
   `claimTerminalNotice` synchronously at the top of the handler (`src/index.ts:4210`), then dies on the
   stale `ctx.sessionManager` getter inside `state.getRunEntries` (`src/state.ts:400-401`); the catch
   downgrades it to `completion-push handler failed for <id>` (`src/index.ts:4233-4236`). The live
   generation then loses the claim and returns silently. The issue body's "send throws first" is wrong;
   both handles are stale but the ctx read is first.
3. **Three writers share one claim set**, and their ordering is what the design must preserve:
   | Writer | Order today | Consequence |
   |---|---|---|
   | wake (`src/index.ts:4210`) | claim → resolve → retry/send | canonical; first terminal event per id wins |
   | poller crash notice (`src/index.ts:2022`) | claim → `pi.sendMessage` (sync) | crash-first wins; a crash *after* the wake is suppressed |
   | abandon (`src/recovery-surface.ts:369`) | claim → `markAgentStopped` (emits `subagent:stopped`) | deliberate crash-first suppression of a boot-abandoned run |
   Because all three claim synchronously inside their own turn, the winner is decided by **turn order**,
   not by any internal `await`. That is the property Design B restores.
4. **Terminal events are emitted synchronously after persistence** (`src/session-manager.ts:2025`,
   `:2059`, `:2125`), and `updateAgentStatus` emits after `persistAgent` (`:1009-1015`, no `pi`), which is
   why family (b) events can still reach the bus during a replacement window even though the settle path
   (family (a)) cannot (`pi.appendEntry` throws first). This asymmetry is unchanged by the fix and is why
   the generation gate — not just the claim — is needed for the shutdown overlap.

## 4. Blocker 1 — the claim protocol (event-first, synchronous, no reservations)

### 4.1 Two candidate protocols, one chosen

| | **P1 — provisional reservation** | **P2 — synchronous validation → committed claim** (chosen) |
|---|---|---|
| Mechanism | Reserve the id before the awaited work with an owner tag; promote to committed after validation; release only if no side effect happened | Do every precondition synchronously, then claim in the same turn; a claim is final |
| States per id | `unclaimed` → `provisional(owner)` → `committed` \| `unclaimed` | `unclaimed` → `committed` |
| Cases it must arbitrate | crash arriving while provisional; provisional holder releases after the crash already lost; duplicate events during the provisional window; two generations' provisionals | none — the window does not exist |
| Failure mode | a crash that lost to a provisional claim which is then released is **silently lost** (the critique's exact warning); a buggy release double-delivers | a validation step that is not actually synchronous would break event-first ordering — prevented structurally (§4.2) |
| Cost | owner-tagged map, release path, arbitration tests | static import + reorder; zero new state |

P2 is feasible only because every precondition is already synchronous:
`getAgent` (`src/session-manager.ts:422`), `state.getRunEntries(ctx)` (`src/state.ts:400`),
`resolveRunEntry`, `buildCompletionMessage`, `resolveDelivery`, `sendCompletionNotification` and
`claimTerminalNotice` are all sync. The *only* await in today's handler is
`await import("./session-manager")` (`src/index.ts:4214`), and that import is cycle-free to hoist
(`grep -rn "from ['\"]\./index" src --include=*.ts | grep -v __tests__` → 0 matches; jiti load probe →
`{"ok":true}`; `tsc --noEmit` → exit 0).

### 4.2 The protocol as implemented (verified prototype, `tsc` 0, 24/24 assertions)

```ts
// src/index.ts — module scope (per module graph)
const TERMINAL_EVENT_TYPES = ["subagent:completed", "subagent:failed", "subagent:stopped"] as const;
let activationSeq = 0;     // factory invocations in THIS graph
let activeGeneration = 0;  // the generation that owns delivery; 0 = none
type GenerationLifecycle = "created" | "active" | "stopped";

// import { getAgent } from "./session-manager";   // STATIC — ordering requirement

function deliverCompletionAlert(event: SubagentEvent): void {   // was async
  const id = event.agentId;
  if (!ownsCurrentSession()) return;                 // 1. ownership gate (sync)
  const ctx = sessionCtx;
  if (!ctx) { log.warn("completion wake skipped — no live session context", …); return; }   // 2. no claim
  if (!id) { log.warn(…); return; }
  const agent = getAgent(id);                        // 3. sync lookup
  if (!agent) { log.warn("completion wake skipped — unknown or pruned agent", …); return; } // no claim
  let run: SubagentRun | undefined;
  try { run = resolveRunEntry(state.getRunEntries(ctx), id); }                              // 4. sync
  catch (err) { log.warn("completion wake skipped — run entry lookup failed", …); return; } // no claim
  if (!claimTerminalNotice(id)) return;              // 5. COMMIT — same turn as the emit
  const knob = state.config.completionNotify ?? "all";
  if (event.type === "subagent:failed" && run && isTransportRetryable(run)) {
    void deliverAfterRetry(ctx, run, knob);          // 6a. async, claim already held
    return;
  }
  sendTerminalNotice(agent, run, knob);              // 6b. sync send, claim held
}
```

Rules that are the protocol (each has a named test in §7):

1. **Sync validation before the claim** — missing ctx / unknown agent / run lookup failure must not consume
   the id (A4, A10). A claim therefore always means "a valid owner existed at claim time".
2. **Claim before the first possibly-asynchronous step** — the retry branch starts only after the claim
   (B4). No duplicate terminal or crash notice can start a second retry while the first is pending.
3. **Never release a claim** — not after a send, not after a spawn, not after a rejection, not after a
   throw. A definite pre-start rejection reuses the *same* claim for its one fallback notice (A13, B2).
4. **A send throw is ambiguous** — the claim is retained and the uncertainty is logged
   (`completion wake send threw — acceptance unknown …`), never retried (A12 both modes).
5. **No provisional state** — there is no code path that adds then deletes an id.

### 4.3 Participant ordering and the full case matrix

| # | Situation | Expected | Pinned by |
|---|---|---|---|
| 1 | one live generation, one terminal event | one notice, payload/options from the 9-row matrix | A1 (×9) |
| 2 | duplicate terminal event (same id) | second sees the committed claim → no-op | A7 |
| 3 | **event first**, crash notice claims in the same turn | crash loses; canonical completion delivered (retry eligible) | A8 (**this is the critique's Major 1 pin**) |
| 4 | **crash first**, terminal event afterwards | crash notice delivered; wake suppressed; no retry | A9 |
| 5 | boot abandon (`claimTerminalNotice` then `markAgentStopped`) | claim precedes its own `subagent:stopped` emit → wake suppressed (unchanged) | existing `recovery-surface` suite (unchanged, green) |
| 6 | loaded but not started (no `session_start` yet) | **no listener exists** → no claim, no stale read; a later generation can deliver | A4 |
| 7 | generation shut down | listener removed → no claim | A5, A6 |
| 8 | obsolete generation whose shutdown never ran | gate drops before touching any handle → no claim, no log noise | A3 |
| 9 | unknown / pruned agent id | no claim; a later valid event for the same id delivers | A10 |
| 10 | run-entry lookup throws | no claim, logged | code path (defensive catch) |
| 11 | duplicate event while the retry spawn is pending | claim already held → exactly one spawn | B4 |
| 12 | send throws before or after acceptance | one attempt, claim retained, uncertainty logged | A12 (×2) |
| 13 | retry rejected pre-start | one source notice under the same claim | A13, B2 |

Two implementation traps that this protocol exists to prevent — both were measured:

- **Claim-last with an awaited import is invalid.** Baseline claims first and passes A8; a claim-last
  variant that awaits the import loses A8 (the critique measured `crashWon=true, sends=0`). P2 is only
  allowed because the claim moved *and* the await disappeared.
- **Claim-first poisons ids on validation failure.** Baseline fails A10: an event for an id with no agent
  record consumes the claim, and the later valid event is suppressed forever.

### 4.4 The 200-id cap boundary (stated, not expanded)

`markTerminalSeen` (`src/notify-completion.ts:266-272`) does `seen.add(id); if (seen.size > 200) seen.clear()`.
The 201st claim therefore **clears the set including the id it just added**, so an immediate duplicate for
that id claims again and delivers twice. Measured identically on the control and the design
(`A11 CAP-RACE {"sends":2}`). This is pre-existing and is **not** a #437 regression.

Therefore the guarantee this design makes is:

> at most one terminal notice per run id **while that id remains inside the existing 200-id retention
> window**; the overflow boundary retains nothing, and the design does not promise exactly-once beyond it.

The design keeps that boundary unchanged (scope discipline: the maintainer asked to preserve existing
dedupe semantics) and pins it with A11 so it cannot drift silently. A minimal correction is available as a
separate decision — **D1** in §8.4: retain the just-claimed id on overflow (`seen.clear(); seen.add(id)`)
so the *current* run cannot double-deliver while older ids are still forgotten; it changes the existing
expectation at `src/__tests__/notify-completion.test.ts:445-452` (`id-0` claims again) and is therefore a
separate, reviewable decision — not part of this fix.

### 5.2 Point of no return and the classification contract

**Point of no return: step 14.** `spawnBackgroundSession` returns only after `session.prompt()` has been
invoked (steps 15-16 cannot throw), so:

> **Contract:** `startBackgroundAgent` returning normally ⟺ a background session exists and its prompt was
> issued. `spawnBackgroundRun` throwing or returning `isError` ⟺ **no prompt was issued**.

The contract is enforced by two mechanisms, both verified:

1. **Containment of the post-spawn tail** (step 17): the monitor/bookkeeping work is best-effort. A
   throwing `ctx.ui` after a started spawn must not propagate into `spawnBackgroundRun`'s `isError` path.
   Without this, a started dispatch is reported as `Failed to spawn background agent` and a started retry
   sends a false source notice (measured: control `B1 spawnCalls=1, sourceMessages=1`).
2. **An explicit `onStarted` callback fired at step 16**, passed only by the retry caller. It converts the
   contract into an observable signal, so the catch branch can distinguish cases even if a future change
   adds a throwing step between 14 and 16.

Three outcome classes, and what each one does:

| Class | Observable | Policy |
|---|---|---|
| **definite pre-start rejection** | gate rejection (`isError`) or a throw with `started === false` | exactly one fallback source notice, under the claim already held; no toast |
| **committed started retry** | `spawnBackgroundSession` returned / `onStarted` fired | suppress the source notice (the retry's own settle is the wake); never cancel, never re-classify as a failure |
| **outcome-unknown** | started, then a throw on the retry path; or `pi.sendMessage` threw | keep the claim, log the uncertainty, never repeat the irreversible step (no second spawn, no second send) |

`scheduleTransportRetry` therefore returns **`true` = the retry was committed** (not "it succeeded") and
**`false` = it was never started**:

```ts
let started = false;
const markStarted = (): void => { started = true; };
try {
  … prelude …
  if (!ownsCurrentSession()) { log.warn("Transport auto-retry skipped — session was replaced", …); return false; }
  const result = await spawnBackgroundRun(pi, ctx, retryParams, task, run, preamble, markStarted);
  if (result.isError) { log.warn("Transport auto-retry spawn rejected — surfacing the original failure", …); return started; }
} catch (err) {
  if (started) log.warn("Transport auto-retry started, then the retry path threw — suppressing the source notice (outcome unknown)", …);
  else         log.warn("Transport auto-retry spawn failed before start — surfacing the original failure", …);
  return started;
}
log.info("Background run settled — transport auto-retry scheduled", …);
try { ctx.ui.notify(TRANSPORT_RETRY_TOAST, "warning"); }
catch (err) { log.warn("Transport auto-retry toast failed — the retry is already running", …); }
return true;
```

Alternatives considered and rejected: returning a typed `SpawnOutcome` union from `spawnBackgroundRun`
would change the result shape of every background dispatch path (single, fan-out, graph) for the benefit of
one caller; an `AsyncLocalStorage`-style cancellation context is a new mechanism for a 6-line check.
### 5.3 What the caller does with the classification

```ts
async function deliverAfterRetry(ctx, run, knob): Promise<void> {
  const agent = getAgent(run.id);
  const fallback = agent ? () => sendTerminalNotice(agent, run, knob) : undefined; // built pre-await
  let committed = false;
  try { committed = await scheduleTransportRetry(ctx, run); }
  catch (err) { log.warn("Transport auto-retry path threw unexpectedly", …); }     // defensive only
  if (!ownsCurrentSession()) { log.warn("completion wake dropped — session was replaced during the transport retry", …); return; }
  if (committed) return;          // the retry's own settle is the wake
  if (fallback) attemptSend(run.id, fallback);   // exactly one fallback, same claim
}
```

Both branches keep the claim; neither releases it. `attemptSend` logs
`completion wake send threw — acceptance unknown (claim retained; run retrievable via get_subagent_result)`
and does not retry.

| Probe | Control (`base2`) | Design (`s1`) |
|---|---|---|
| spawned session, then `ctx.ui` throws on the repaint (B1) | 1 spawn, **1 source notice** (false failure) | 1 spawn, **0 source notices**, `footer repaint failed` logged |
| spawn throws before start (B2) | 1 source notice | 1 source notice |
| started retry, then toast throws (B3) | **1 source notice** / no toast log | 0 source notices, `toast failed` logged |
| two failed events during a deferred spawn (B4) | 1 spawn | 1 spawn |
| replacement during the retry prelude (B5) | **1 spawn invoked after ownership loss** | **0 spawns**, `retry skipped` logged, claim held |

| shutdown reap throws (B7) | n/a | shutdown resolves; listeners already gone; next generation delivers once |

### 5.5 Scope: what is cancelled, what is not, and the honest bound

- **In scope (implemented):** a retry is not *begun* after ownership is lost during its awaited prelude;
  a started retry is never reported as a source failure; a started retry's toast cannot change the
  classification; the source notice is suppressed exactly when a retry was committed.
- **Explicitly out of scope (not claimed):** cancelling a spawn that has already been invoked. Once
  `session.prompt()` has run (step 14), the session belongs to the old runtime; a `/new` during it cannot
  revoke it, and no guard in this design pretends otherwise. Its later settle is (per the maintainer
  policy) a straddling run: delivery is best-effort and not guaranteed.
- **Residual to document in the PR:** a replacement landing between step 9 and step 14 leaves a partially
  created session: an agent record with status `running`, a session directory, and (from step 11) an
  inflight registry entry, because `registerInflightRun` runs *before* `pi.appendEntry`. The next boot will
  mark that registry entry interrupted and may offer a phantom recovery notice for a retry that never
  prompted. This is pre-existing behaviour for any spawn failure in that window, not introduced by #437,
  but the retry path makes it reachable. **D2** (§8.4) offers the exact fix (a pre-prompt ownership
  checkpoint plus cleanup) as a separate decision, because it touches the spawn lifecycle shared with
  normal dispatch.

## 6. Blocker 3 — per-generation lifecycle ownership

### 6.1 State machine (explicit, per factory invocation)

| State | Meaning | Listeners | May deliver |
|---|---|---|---|
| `created` | factory ran, no `session_start` yet | none | no |
| `active` | this generation owns the live session | 3 (one per terminal type) | yes, if `generation === activationSeq` **and** `activeGeneration === generation` |
| `stopped` | `session_shutdown` observed | none | no |

Transitions:

| From → To | Trigger | Guard | Action |
|---|---|---|---|
| `created` → `active` | `session_start(ctx)` | `generation === activationSeq` | set `sessionCtx`, `activeGeneration = generation`, subscribe |
| `active` → `active` | duplicate `session_start` | same | refresh `sessionCtx` only (idempotent; no re-subscribe) |
| `active` → `stopped` | `session_shutdown` | none | `activeGeneration = 0` **if ours**, then `off` exactly our listens |
| `stopped` → `active` | later `session_start` on the same instance | `generation === activationSeq` | re-subscribe, re-own (this is the "the host invited me to serve this session" transition; it is what the repo's existing recovery tests rely on) |
| `stopped` → `stopped` | duplicate `session_shutdown` | none | no-op |
| older generation, any state, receives `session_start` | — | `generation !== activationSeq` | **rejected**, log `session_start ignored — this extension generation is not the newest` |

Why this ordering and not candidate C's: candidate C released ownership and unsubscribed in a `finally`
*after* the shutdown body's awaits (including `reapActiveChildren`). That leaves an overlap window where
the generation no longer owns the session but still subscribes and still has valid handles — so it can
deliver twice. Deactivating **first**, synchronously, closes the window; and because the off happens before
any await, a throwing cleanup cannot skip it (B7 measured).

### 6.2 Hook bodies (exact order)

```ts
pi.on("session_start", async (_event, ctx) => {
  if (!activateGeneration(ctx)) { log.warn("session_start ignored — …"); return; }   // 1. sync, first
  setLogCwd(ctx.cwd); …existing body…                                               // 2. unchanged
});

pi.on("session_shutdown", async (_event, _ctx) => {
  deactivateGeneration();                                     // 1. sync: ownership off + exact unsubscribe
  log.info("Session shutting down", …);                       // 2. unchanged
  try { await reapActiveChildren(log); } catch { … }          // 3. unchanged, now cannot leak listeners
  cleanupSessionState(state);                                 // 4. unchanged
  recoveryNoticeDelivered = false;                            // 5. unchanged
});
```

### 6.3 Subscription identity (exact, idempotent, unrelated consumers safe)

```ts
const terminalSubscriptions: Array<{ type: TerminalEventType; listener: (e: SubagentEvent) => void }> = [];
function subscribeTerminalListeners(): void {
  if (terminalSubscriptions.length > 0) return;                     // idempotent
  for (const type of TERMINAL_EVENT_TYPES) {
    const listener = (event: SubagentEvent) => { deliverCompletionAlert(event); };
    terminalSubscriptions.push({ type, listener });
    eventBus.on(type, listener);
  }
}
function unsubscribeTerminalListeners(): void {
  for (const { type, listener } of terminalSubscriptions) eventBus.off(type, listener);  // identity delete
  terminalSubscriptions.length = 0;
}
```

`eventBus.off` is `Set.delete(listener)` (`src/event-bus.ts:36-45`), so only the exact registered function
is removed. No `listeners.clear()`, no bus reset, no touching another generation's or another consumer's
subscription (A2/A6 assert an unrelated listener still fires). Repeated generations return the bus to its
baseline count — verified with a test-only `__listenerCounts()` export, because a gated-but-retained
listener is invisible to a wake-count assertion (`m-off` survives A2/A3 but is killed by A6).

### 6.4 Same graph vs fresh graph — what is and is not guaranteed

| Case | Guarantee |
|---|---|
| `/new` on the same loader (shared module graph) | **full**: obsolete generation cannot claim, send, retry or read a stale handle; exact unsubscribe; no growth |
| `/reload` re-evaluating the module (fresh graph) | **full for the new graph**: it has its own bus, token and claim set; the new session's runs are emitted by the new graph's `session-manager` and delivered by the new graph's listener |
| missed shutdown **and** fresh graph, i.e. an old-graph run settling into the old graph's bus | **not covered, and not claimed**: a graph-local token cannot revoke an older graph. Under the maintainer policy such a run straddles the replacement (out of scope). The old graph keeps its own claim set, so it cannot poison the new graph's ids |
| two live generations inside one graph (shutdown overlap) | **full**: only the newest activated generation owns delivery; an old shutdown never revokes the new one (A15) |
| duplicate/late `session_start` delivered to an older factory | **rejected** by `activationSeq` (A14) |

Pi sequencing assumptions (from the investigation's real-loader probes, not re-run here): a replacement
re-invokes the factory against a fresh runtime while reusing the module graph; the old instance receives
`session_shutdown` but never the new `session_start`; `/reload` re-evaluates the module when the host has
bindings. If a future pi reverses any of these, the *token* becomes inert but the unsubscribe still
satisfies the documented cleanup contract — the failure mode degrades to "same as today", never worse.

### 6.5 No-listener windows (stated honestly)

- **Loaded but not started:** no subscribers at all. A terminal event in that window is not claimed and not
  logged by this extension. Acceptable because such an event belongs to the previous session (all runs of
  the new session are created after its `session_start`), and claiming it would be worse.
- **After the last shutdown, before the next start:** same — silence, claim free. No sentinel is proposed
  (decision D3): a sentinel would only add a log line for an out-of-scope straddle and would be a second
  subscription lifetime to reason about.
- **Shutdown overlap:** the old generation is already deactivated, the new one is not active yet; an event
  there is silent. Same reasoning.

### 6.6 Stale handles for normal current-session runs

For a run begun in the current live session, the only way this generation's `pi`/`ctx` becomes stale is a
replacement, and every replacement first deactivates the generation (or makes it the older one), so:
- the listener will not run at all after shutdown (listener removed);
- if the shutdown was missed, the gate drops before any handle read;
- if an event is already inside the handler when the replacement happens, the handler is fully synchronous,
  so there is no suspension point for a replacement to land in — the send either happened before the
  replacement or the generation was already inactive;
- the only asynchronous continuation is the retry branch, which re-checks ownership after its await and
  drops with a log rather than touching stale handles (B6).

### 6.7 Cancellation and uncertainty bounds

- Deactivation is *cooperative*: it stops future claims and future retry starts; it cannot abort work
  already handed to the SDK.
- A started retry may finish in the old runtime after `/new`; its settle is a straddling settle and is not
  guaranteed a wake (policy). The parent's source notice stays suppressed — the retry exists, so a source
  notice would be a duplicate report of a run that is still going.
- If a send throws, the design cannot know whether the message was accepted. It keeps the claim and logs
  the uncertainty; it never re-sends and never releases. "Exactly once" is therefore **not** claimed for the
  throw case — at-most-one-attempt is.

| # | Option | Mechanism | Blast radius | Cost | Failure mode / risk if wrong |

Option A1 is the honest "smallest thing that fixes the observed bug"; it is rejected because it leaves
three of the six critique blockers untouched (Major 3/5/6 partially, Major 1's poisoning). Option A2 is
rejected because it *adds* the arbitration the critique asked to avoid when a synchronous alternative
exists. Option C is the right structural answer to "who owns subscriptions" but not for this fix: the
maintainer asked for a scoped reliability fix, not an eventing migration. Option D is out of scope by
policy and cannot be honest until the straddling settle can emit an event.

### 8.2 Recommendation

**Option B.** Rationale, in order of weight:

1. It is the only option that keeps the *behaviour the baseline already has right* — event-first claim
   winner (A8) and crash-first suppression (A9) — while removing the baseline's two real defects
   (obsolete listener claims first; validation-failure poisoning). The prototype preserves all 9 delivery
   matrix rows and all 80 existing dedupe/retry/notify tests.
2. It removes the entire class of "ambiguous throw" ambiguity at the retry seam by *enforcing* an invariant
   (containment) and *observing* it (`onStarted`), instead of guessing from a `ToolResult`.
3. Its blast radius is one file plus a test-only export; every change is covered by a named test that fails
   on the control, and one mutant is honestly reported as surviving.
4. It makes no promise the host cannot keep: no cross-graph revocation, no cross-replacement delivery, no
   exactly-once beyond the existing retention window.

### 8.3 Falsifiers (what would change the recommendation)

| # | Evidence | Effect |
|---|---|---|
| F1 | a real pi 1.5.0 replacement re-evaluates the extension module (fresh listener `Set`) | the obsolete-listener premise dies; unsubscribe/gating become unnecessary (sync claim still required) — Option A2's claim protocol would suffice |
| F2 | `session_shutdown` is proven to always complete before any next activation, and the host never delivers a late `session_start` to an old factory | the generation gate could be dropped (unsubscribe + synchronous claim would pass A2/A5/A6); A3/A14 are the discriminators |
| F3 | an SDK-level fault injection shows `session.prompt()` can throw **after** the run started, or that `createAgentSession` can start work and fail | the point-of-no-return contract is false; a real outcome enum (`started` / `not-started` / `unknown`) plus cleanup must replace it |
| F4 | `pi.sendMessage` is documented to throw only *before* acceptance | the send-throw case stops being ambiguous; a bounded single re-send could be allowed (it currently must not be) |
| F5 | a live run with the patch reproduces A2 (wake lost, stale warn) | the ownership mechanism is wrong for the host's real ordering (e.g. the host emits terminal events during teardown after `session_shutdown`); the design must re-open |
| F6 | the maintainer decides straddling settles must deliver | Option D becomes necessary; scope and durability work change, and this design is a prerequisite, not the answer |

### 8.4 Decisions still required (the scope policy is taken as given, not re-asked)

- **D1 — 200/201 cap retention.** *Recommended: keep the existing semantics and ship the documented
  residual (A11).* Alternative: one line in `markTerminalSeen` (`seen.clear(); seen.add(id);`) so the
  current id cannot double-deliver at overflow, at the cost of changing
  `src/__tests__/notify-completion.test.ts:443-450` (which asserts `id-0` claims again) and of a 201-entry
  bound. This is a behaviour change to an existing contract, so it needs an explicit yes/no.
- **D2 — partial-spawn cleanup.** *Recommended: follow-up PR, not this fix.* Add a pre-prompt ownership
  checkpoint inside `spawnBackgroundSession` (after the queue wait and immediately before

  `finalizeRunEntry('failed')` best-effort, prune the new session dir) so a replacement mid-spawn leaves no

- **D3 — sentinel for the no-listener window.** *Recommended: no.* A module-level logger-only subscriber

  never be traceless" is made a hard requirement, it becomes a product decision with its own test.

## 10. Design assumptions (paste into the PR)

1. **State created and where.** In-process only. Module scope per module graph: `activationSeq`,
   `activeGeneration`, and the existing `terminalClaims` `Set` (`src/notify-completion.ts:279`, ≤200/201
   ids) plus the bus's listener Sets. Per factory invocation: `generation`, `lifecycle`,
   `terminalSubscriptions` (closures). Nothing on disk, no permissions, no new files. Graph-local by
   construction: a fresh module graph gets fresh instances.
2. **Teardown and crash window.** `session_shutdown` → `deactivateGeneration()` synchronously (release
   ownership if ours, then `off` exactly our listener identities), then the existing reap/cleanup. If the
   process dies, all of it dies with the process (no sweep needed). If the host never calls shutdown, the
   listeners remain but are inert (gate: not the active generation) and cannot claim or read a stale
   handle; the next generation supersedes them. A fresh-graph reload discards the graph.
3. **Concurrency model.** Single-threaded event loop; the terminal handler is fully synchronous
   (gate → validate → claim → send), so two events cannot interleave; the retry branch's claim is taken
   before its first await, so a duplicate cannot start a second retry. Arbitration is `Set.add` in
   `markTerminalSeen`. No lock or queue is introduced.
4. **Missing / partial / unreadable state.** Fail-closed for delivery: no ctx / no agent / run lookup error →
   no claim, no send, warn. A committed claim is never released (fail-closed against duplicates) even when
   the send or spawn outcome is unknowable; the uncertainty is logged. The `off`/`failed` delivery matrix is
   untouched.
5. **Evidence per claim.** §11 + `/tmp/brl437-design-437-bank.md`: the control's red assertions, the
   prototype's green assertions, the single-site mutant ledger (including one surviving mutant), `tsc` exit
   0 on both, jiti load of the patched extension, and the identical full-suite failure set on control and
   prototype (copy artifacts only).

## 12. Residual risks and follow-ups

- **Poller crash notices** (`src/index.ts:2021-2033`, `2056+`) still use the spawning generation's `pi`
  and claim before sending. A stale poller can consume an id and then throw. Unchanged by this design; it
  belongs to the straddling-run follow-up and needs its own ownership decision.
- **Straddling settle durability**: a run that settles after its runtime is invalidated emits no terminal
  event (`pi.appendEntry` throws first; `markTerminalBestEffort` does not emit). Not fixed here; it is why
  no cross-replacement delivery is promised.
- **Phantom interrupted record** for a replacement between `createAgentSession` and `session.prompt` (D2).
- **`sendMessage` ambiguity** is logged, not resolved; a future host acknowledgement (or a documented
  "throws only before acceptance") would allow a bounded improvement (F4).
- **Live acceptance** must be maintainer-triggered, on the fixed install, and must record the straddling
  case as a confirmation of the boundary, not as a success criterion. A merged extension change opens the
  existing release checkpoint; no release without maintainer approval.
