# Issue #449 — triage / reachability probe

**Question.** Can the REAL pi 1.5.0 SDK settle a background session successfully with **zero assistant
messages** — i.e. produce exactly what our settle classification records as
`completed / done / stopReason "stop" / exitCode 0 / turns 0 / output ""`?

**REACHABLE: yes.** Demonstrated end-to-end with the real `spawnBackgroundSession` + the real
`@earendil-works/pi-coding-agent@1.5.0` session (real AgentSession, real anthropic-messages wire code,
real HTTP + SSE parsing) against a loopback fake provider. No production code was changed
(worktree clean at `2972d61`).

**But the trigger is not the one the issue hypothesises.** A dropped connection, a 500/401, an
`event: error`, an empty body, a `message_stop`-only stream, or a mid-run abort each land as **one
assistant message with `stopReason "error" | "aborted"`** and are correctly recorded as
`failed`/`stopped` — `runWithLifecycle`'s `handleRunFailure` makes a silent drop unreachable. What *is*
reachable is a **truncation** (`stop_reason: "max_tokens"` ⇒ `stopReason "length"`) whose assistant
message the SDK **deliberately omits from the model projection** before the run settles. When the
branch is too short for the recovery compaction to run, that omission is unconditional: the run then
settles with the assistant message gone, `prompt()` resolves, and the extension records a **false
success with `turns: 0`, `output ""`, and the completion message saying "category: success"**.

## 4. The reachable path, in detail

Provider turn (real wire): `message_delta.delta.stop_reason = "max_tokens"`, and
`usage.output_tokens` is **lower than `model.maxTokens`** (the number pi asked for, when it asked for
the model maximum). pi maps that to `stopReason: "length"`
(`pi-ai/dist/api/anthropic-messages` `mapStopReason`, bundled at
`pi-coding-agent/dist/bundle/chunks/anthropic-messages-BWGCKOF4.js`), the message is emitted normally
(`message_end`, persisted as a session `message` entry), and then:

1. `_handlePostAgentRun` (`agent-session.js:1549-1583`) calls `_checkCompaction(message)`.
2. `_checkCompaction` (`:2409-2496`) computes
   `recoverableLength = sameModel && assistantIsProjected && isRecoverableLength(message, model.maxTokens)`
   (`:2455`). `isRecoverableLength` is `stopReason === "length" && desiredMaxOutput > 0 && usage.output < desiredMaxOutput`
   (`pi-ai/dist/utils/overflow.js`) — note the comparison is against **`model.maxTokens`**, not the
   per-request (context-clamped) value.
3. Because there has been no prior recovery attempt, it calls
   `_omitRecoveryAttempt(assistantMessage)` (`:2486`) → a `context_edit` entry with
   `replacement: null` (`:856-884`) → `_refreshFinalizedContext()` → **`agent.state.messages` is
   replaced by the projection, and the assistant message is gone**.
4. It then calls `_runAutoCompaction("overflow", willRetry=true)`. With a short branch,
   `prepareCompaction` returns `undefined` (`dist/core/compaction/compaction.js:609-643` — nothing
   older than `keepRecentTokens = 20000` to summarise) → `_runAutoCompaction` → `false` → **no
   compact-and-retry ever happens**.
5. The run settles: `_emitAgentSettled`, `prompt()` **resolves**.

So the message was never lost on the wire, never rejected, and never reported as an error: the SDK
removed it from the view our settle reads, on purpose, as step 1 of a two-step recovery whose second
step was skipped.

Measured proof of the mechanism (probe `focus-length2.test.ts`):

```

          "_runAutoCompaction(overflow, willRetry=true) -> false",
          "agent_settled"]
sessionMessages: [system, user]
branchEntries:   [model_change, thinking_level_change, message, message, message, context_edit(target)[null]]
overflowRecoveryAttempted: true
```

**End-to-end, real `spawnBackgroundSession` + real SDK (probe `p5-e2e.test.ts`), compaction at its
default (`enabled: true`):**

```

agent.result: { exitCode: 0, usage: {input:0, output:0, cost:0, turns:0} }   // no stopReason field
finalOutput: ""
run entry:   { status: "done", stopReason: "stop", turns: 0, tokensIn: 0, tokensOut: 0,
               outputSummary: "", finalTurnError: false }

```

That is E1's record, produced without a stub.

Boundary, same probe with `compaction.enabled = false`:

```

```

so the false success is **gated on the SDK's compaction setting being enabled**, which is the default
(`pi-coding-agent/dist/core/settings-defaults.js:8-11`).

## 5. The honest boundary: SDK-producible vs provider-plausible

| Case | SDK produces it? | A real provider could? | Evidence |
|---|---|---|---|
| Zero assistant messages via a **dropped/failed response** | **No** | No | §3 rows f-l: every one writes `stopReason "error"` (`agent.js:369-389`) |
| Zero assistant messages via **abort** | No (aborted message written) | No | §3 row d |
| Zero assistant messages via **prompt short-circuit** | Yes (code) | **No** | `agent-session.js:1650-1674`; needs extensions/concurrency the spawn disables |
| Zero assistant messages via **`length` omission** | **Yes** | **Yes, under two ordinary conditions** | §4 |
| Zero assistant messages via **retry-abort** | Yes | Yes (any retryable error + a timeout abort inside the backoff) | §3 P2; masked by our pre-stamp |

Why "a real provider could" for the `length` row — two independent, ordinary triggers:

1. **Provider-side under-delivery.** `isRecoverableLength` fires whenever the provider stops on
   `max_tokens` while reporting fewer output tokens than `model.maxTokens`. That is exactly what a
   catalog-vs-provider `maxTokens` mismatch produces (gateway/proxy caps, catalog drift, custom
   `models.json` providers). pi's own `overflow.js` documents at least one family that does this:
   Xiaomi MiMo returns `finish_reason "length"` with `output = 0`.
2. **Context-clamped request.** `buildBaseOptions` sets every request's `max_tokens` to
   `min(model.maxTokens, contextWindow − estimateContextTokens − 4096)`
   (`pi-ai/dist/api/simple-options.js:5-10,23`). When the prompt is large enough for the clamp to
   bite and the provider fills that reduced budget, `usage.output == requested < model.maxTokens` →
   recoverable. For the *exact* zero-message shape this must be the run's **first** assistant response
   (a big initial task/context), because a later truncation leaves earlier assistant messages in place
   (§3 P3) and the record then says `failed / incomplete` instead.

**What I could not execute:** an actual vendor endpoint (no network inference permitted here), so the
fine print is "the SDK turns this provider output into the false-success record — measured end to
end; that a vendor emits this output is argued from pi's own clamp and its documented provider list,
not measured against a vendor."

## 7. Secondary (currently masked) path — for the record

`agent-session.js:3108-3140`: a retryable provider error is **also** omitted from the projection
before the retry backoff sleeps. If the sleep is aborted (`session.abort()` → `abortRetry()` →
`_finishCancelledRetry`), the loop exits with **zero assistant messages** and `prompt()` resolves
(measured, §3 P2). Every abort call site in our code pre-sets `status = 'stopped'`
(`src/session-manager.ts:1110`, `:1930`, `src/index.ts:2206`), and `:1958` takes the aborted branch on
that status, so today this lands as `stopped` rather than `completed`. It is not a live false success,
but it is a second way the "no assistant message" state can arise from a **real provider error**
(HTTP 529/overloaded is routine), so a fix that keys on `turns === 0` alone should know about it.

## 8. What I did not establish

- **No vendor endpoint was contacted.** The provider-side output that starts the chain is exercised
  over loopback with the real wire code, not against Anthropic/OpenAI/etc.
- **No real-vendor frequency estimate.** I can say the trigger is ordinary (catalog maxTokens mismatch,
  context clamp, documented MiMo behaviour); I cannot say how often it happens in the wild.
- **The zero-message outcome requires a branch too short to compact.** For long sessions the SDK's
  recovery compaction usually runs (an extra LLM call) and the retry writes a new assistant message —
  then the record is either a genuine answer or a `failed/truncated` from the *second* truncation.
  I measured the short-branch case; I did not drive a long-session compaction end to end.
- **`openai-*` / other provider APIs** were not driven; the omission lives in `AgentSession`
  (above the provider layer) so it is provider-agnostic by construction, but that is reasoning, not a
  measurement.
- Everything here is scratch-only: no repo file was written, no test was added to the suite, no commit
  was made (`git status` clean).

## 9. Comment-ready summary (for #449)

> **Reachability: yes — but not via a silent drop.** Probed with the real pi 1.5.0 SDK (real
> `AgentSession`, real anthropic-messages wire code, loopback fake provider, no paid inference) and
> with the real `spawnBackgroundSession`.
>
> A dropped connection cannot produce the E1 record: every failure shape I could produce — socket
> destroyed before the first event, HTTP 500, HTTP 401, SSE `event: error`, 200 with an empty body, a
> `message_stop`-only body, and a mid-run abort — lands as exactly one assistant message with
> `stopReason "error" | "aborted"`, and is correctly recorded `failed` / `stopped`. `runWithLifecycle`
> → `handleRunFailure` (`pi-agent-core/dist/agent.js:345-389`) guarantees that.
>
> The record *is* reachable through a different door: a truncated turn. When a provider answers with
> `stop_reason: "max_tokens"` and reports fewer output tokens than `model.maxTokens`,
> `_checkCompaction` classifies it as a "recoverable length"
> (`isRecoverableLength`, `pi-ai/dist/utils/overflow.js`) and calls `_omitRecoveryAttempt`
> (`agent-session.js:2486`), which persists a `context_edit` that removes the assistant message from
> the model projection and then refreshes `agent.state.messages` from that projection
> (`agent-session.js:583-589`). It then attempts the compact-and-retry — and if the branch is younger
> than `keepRecentTokens` (i.e. the run's own first turn), `prepareCompaction` returns `undefined`, so
> the retry never happens and the omission stands.
>
> End-to-end measurement (real spawn, compaction at its default `enabled: true`):
> `agent.status = "completed"`, `result.exitCode = 0`, `usage.turns = 0`, `finalOutput = ""`,
> run entry `{status: "done", stopReason: "stop", turns: 0, tokensIn: 0, tokensOut: 0}`,
> completion message `"completed … category: success"` with an empty body, SDK session dir pruned.
> That is E1's record byte for byte. Setting `compaction.enabled = false` makes the same turn record
> `failed / truncated / turns: 1`, so the false success is gated on the SDK compaction default.
>
> So #449 should not be closed as unreachable. Its stated cause ("a drop is reported as success") is
> wrong; the real shape is "a truncated turn is omitted from the projection, the recovery retry is
> skipped, and the settle reads a zero-assistant-message session as a success". Two ordinary provider
> conditions get there: a provider whose real output cap is below the catalog's `maxTokens` (pi's own
> `overflow.js` documents Xiaomi MiMo returning `length` with `output 0`), and a context-clamped
> request (`clampMaxTokensToContext`, `pi-ai/dist/api/simple-options.js:5-10`) where the provider fills
> the reduced budget on the run's first turn. Frequency is unmeasured; the mechanism is not
> hypothetical.
>
> Secondary, currently masked: a retryable provider error (e.g. 529) is also omitted before the retry
> backoff, so an abort during that sleep also leaves zero assistant messages and a resolved prompt;
> every abort call site in our code pre-stamps `status = 'stopped'`, so that one settles `stopped`
> rather than `completed`.
