## ERRATA — Unit 2 premise corrected (2026-10-12, implementation round)

The Unit 2 premise above is WRONG and the implementation it specced was reverted. Verified facts:

- `state.getRunEntries` ends with `cleanupRuns(runs, this.config.maxHistoryEntries)` (`src/state.ts`);
  `cleanupRuns` (`src/history.ts`) sorts NEWEST-FIRST by `startedAt` for any non-zero limit (its own
  comment: "Always sort newest-first for consistency"). The session runs `maxHistoryEntries: 500`
  (verified in the live session file).
- Therefore run history was ALREADY newest-first; the interrupted row sat at the BOTTOM solely
  because the U3 bridge APPENDS synthetic rows (`[...sessionEntries, ...synthetic]`).
- The retry menu's `.reverse()` flips the newest-first source into OLDEST-first — the two surfaces
  disagreed in the OPPOSITE direction from what Unit 2 assumed.
- Root cause of the wrong premise: a partial read of `getRunEntries` (stopped before the `cleanupRuns`
  call) — Rule 19 partial-read class.

**Corrected Unit 2 (implemented on PR #332, correction round):**
1. `src/history.ts` — shared newest-first sort helper extracted from `cleanupRuns`; `cleanupRuns`
   sorts even when `maxEntries === 0`.
2. `src/recovery-surface.ts` — `visibleRunEntries` merges synthetic rows into recency position
   (ordered union; by-reference contract preserved when nothing is added).
3. `src/tui.ts` — retry menu drops `.reverse()`; history keeps the already-newest-first order; the
   reverse-based `newestFirst` helper from the first attempt is deleted.
